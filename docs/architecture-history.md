## Task #148 — 503 Attribution

Every `503 service_busy` response funnels through `server/middleware/service-busy.ts` (`emitServiceBusy` / `recordServiceBusy`). One structured `[503]` log line per emission (with rid/method/path/route/source/kind/code/pool active+idle+total+waiting+saturation/lease — guaranteed per-request attribution from logs alone) + a 50-event in-memory ring buffer + the cross-cutting `critsend_service_busy_503_total{source,route}` counter make every emission attributable. Sources: `load_shed`, `lease_exceeded`, `checkout_timeout` (incl. `kind=upgraded_from_500` from the `poolErrorResponseUpgrade` patch), `handler_transient` (route-level transient DB error), `memory_pressure` (POST `/campaigns/:id/send`). Triage endpoint: **GET `/api/admin/503-attribution`** (admin-gated via `users.is_admin`/`ADMIN_USER_IDS`) returns total + per-source + per-route + per-pair counts plus the most-recent ring entries with rid, route, pool snapshot and lease holding. Frontend `apiRequest` now throws `ApiError` (with `.status` + parsed `.body`); the `/campaigns` page recognises 503 service_busy and shows a soft "Serveur momentanément occupé — Nouvelle tentative…" panel instead of the red error banner. The counter-reconciler push-downs the `recent_campaigns` filter INTO each `truth` CTE so each tick scans the active subset (~100 campaigns) instead of the full 20 M-row `campaign_stats` table — eliminating the recurring `statement_timeout` ticks that previously consumed a pool slot for 120 s. POST `/api/campaigns` validates `segmentId` + `excludeSegmentId` in a single `WHERE id = ANY(...)` round-trip so the route stays under the 2-checkout-per-request lease cap.

## Task #154 — Pressure-Guard SMTP Fan-Out

During the same 2026-05-14 prod incident the parallelized drain (Task #153) was confirmed running with `drained_calls=9` per tick, but cumulative throughput plateaued at ~800-3500 sends/min — far below the 24k/min projection. Root-cause: inside `drainCampaign`, the SMTP dispatch loop was **strictly sequential** (`for (const sub of eligibleSubs) { await sendEmailWithNullsink(...) }`), so each send waited for the previous SMTP RTT (~100ms) before starting the next. Per-campaign ceiling = ~10 sends/sec, × DRAIN_PARALLELISM=4 = ~2,400/min — exactly the observed rate. **Fix**: bounded-parallel SMTP fan-out inside `drainCampaign` using the same worker-pool pattern as Task #153 but at the per-send level. N workers (default `PRESSURE_GUARD_SMTP_CONCURRENCY=20`, hard-capped at 100) pull from a shared `sendQueue` of eligible subscribers; SMTP I/O is interleaved while Node's single-threaded event loop keeps `successIds`/`failedIds`.push race-free between awaits. With DRAIN_PARALLELISM=4 × SMTP_CONCURRENCY=20 the theoretical cluster-wide ceiling becomes ~80 simultaneous SMTP sends → ~24k sends/min. Peak fan-out is bounded by the Nodemailer pool per MTA (typically 5-10 conn × 7 MTAs = 35-70 sockets) so the 80 cap fits comfortably. The env var is persisted in both `critsend-web` and `critsend-worker` env_production blocks of `deploy/ecosystem.config.cjs`. Startup log line now includes `smtp-concurrency=N`. Diagnostic note: the previous bottleneck was invisible in the standard tick log (`drained_calls=N` counts `drainCampaign` invocations, not actual SMTP sends), so the symptom was "drain looks healthy but backlog grows" — only the per-MTA `recent_sent` query revealed the throughput plateau. Companion lesson: if the deferred queue starts to grow despite `leader_acquired=Y` and non-zero `drained_calls`, check the actual sends/min via `SELECT date_trunc('minute', sent_at), COUNT(*) FROM campaign_sends WHERE sent_at > NOW() - INTERVAL '10 min' AND status='sent' GROUP BY 1` before assuming the drain is broken.

## Task #153 — Pressure-Guard Drain Parallelization

The pressure-guard deferred-drain worker (server/workers/pressure-guard-worker.ts) previously processed eligible campaigns strictly sequentially — `for (const row of campaignsRes.rows) { await drainCampaign(...) }` — which capped per-tick throughput at ~1 campaign × BATCH rows / drain-duration. Constated during the 2026-05-14 prod incident: 10+ massive campaigns launched in parallel at 12:32-12:34 UTC on overlapping audiences pushed 810k rows into the deferred queue (321k immediately `due_now`, 488k still inside the 6h pressure window), but the sequential drain produced only ~1500 sends/min total — projected ~3-4 hours to drain. **Fix**: bounded-parallel drain with a fixed concurrency cap. The drain loop now spawns N workers (default `PRESSURE_GUARD_DRAIN_PARALLELISM=1`, prod set to 4 via deploy/ecosystem.config.cjs) that pull from a shared queue of eligible campaign IDs. Each `drainCampaign(campaignId)` call peaks at ~2 main-pool connections (claim txn + finalize txn; SMTP send is external I/O), so DRAIN_PARALLELISM=4 holds peak DB footprint at ~8 connections — well within the 30-slot main pool. JS single-threaded execution makes the `drainedCalls`/`errorCount` shared counter increments race-free despite interleaved awaits. The cap is hard-clamped to 16 to prevent runaway pool saturation if misconfigured. Companion change: deploy/ecosystem.config.cjs now persists the production-tuned drain knobs (`PRESSURE_GUARD_POLL_MS=10000`, `PRESSURE_GUARD_BATCH=1000`, `PRESSURE_GUARD_MAX_CAMPAIGNS=20`, `PRESSURE_GUARD_DRAIN_PARALLELISM=4`) into both `critsend-web` and `critsend-worker` env_production blocks so they survive `pm2 reload` / restart cycles (previously the same values were applied via one-shot `pm2 restart all --update-env` which is lost on the next ecosystem reload). All four are dotenvVars-overridable, so `.env` still wins for ad-hoc tuning. The "Starting" log line now includes `drain-parallelism=N` so per-process configuration is grepable. **Architectural note**: the drain is started from BOTH the web (DISABLE_WORKERS branch in server/index.ts) AND the worker process; only one acquires the leader lease at a time (Task #149 lease table), so the env vars MUST match on both sides — they do, via the shared dotenvVars+default mechanism.

## Task #152 — Bootstrap Lock Self-Heal

At every web/worker process boot, `releaseStuckBootstrapLocks()` (server/bootstrap-lock-recovery.ts) preemptively `pg_terminate_backend`s any idle PgBouncer-labelled backend (`application_name='pgbouncer'`, `state IN ('idle','idle in transaction','idle in transaction (aborted)')`) still holding a session-level advisory lock in our reserved bootstrap range (objids 900001-900020). This neutralises the Neon-PgBouncer transaction-pooling leak that `withAdvisoryLock` (server/bootstrap-lock.ts) suffers from on every `pm2 reload`: the previous process's `pg_try_advisory_lock(<objid>)` lands on backend X via PgBouncer, the Node process exits, but PgBouncer keeps backend X alive (idle) and the session lock leaks indefinitely — the next process boots, tries `pg_try_advisory_lock` on a different backend, gets `acquired=false`, logs "Another process is running bootstrap — skipping" and bails, so the bootstrap DDL never runs on the new code. Without this self-heal, Task #149's deploy hung in production with `pressure_guard_leader` table never created and `bootstrap=pending → deferred` looping every 15s for 6+ minutes until manual `pg_terminate_backend` via psql freed the leaked PIDs (constated 16564/16571/16609 holding objids 900004/900005/900015). The self-heal SQL is identical to `POST /api/admin/pressure-guard/release-stuck-locks` (still kept as a manual one-shot escape hatch, but no longer needed during normal deploys) but generalised to the full 900001-900020 range and called automatically. Best-effort: never throws, 5s `statement_timeout`, terminates only `application_name='pgbouncer'` idle backends so direct app connections are never touched. Logs `[LOCK_RECOVERY] (web-boot|worker-boot) terminated N leaked PgBouncer backends … by_objid={…}` on every boot for observability.

## Task #160 — Drain Process Isolation & Bulletproof Deploy

The 2026-05-15 prod incident (1h30 user-facing freeze) had three root causes that this task addresses together. **(1) Snowball ratio frozen on cumulative counters**: the sender's auto-throttle read `processed = campaigns.sent_count + failed_count` (incrementally maintained, drift-prone). When the drift desynced from the real-time deferred backlog, the ratio plateaued at 0.801 and the sender slept forever in the throttle branch even after the drain had emptied the queue. Fix: both numerator and denominator now come from a single `COUNT(*) FILTER (...)` over `campaign_sends`, with a 30s in-memory per-campaign cache (`PRESSURE_RATIO_CACHE_TTL_MS`) to keep per-iteration cost bounded. **(2) Drain process competing with web/worker for resources**: the embedded drain in both `server/index.ts` (DISABLE_WORKERS branch) and `server/workers.ts` shared the main DB pool with HTTP requests and import processing — a stalled query in either could starve the drain via pool saturation. Fix: a new dedicated `critsend-drainer` PM2 process (`server/drainer-main.ts` → `dist/drainer-main.cjs`) runs ONLY the pressure-guard worker with its own `DRAINER_PG_POOL_MAX=6` pool and `PROCESS_TYPE=drainer` (recognised in `server/connection-budget.ts`). The embedded drain is skipped on web/worker when `DRAIN_PROCESS_DEDICATED=true` (default in production via `deploy/ecosystem.config.cjs`); the existing leader-lease (`pressure_guard_leader` table) still keeps things safe during a partial rollout — only one process drains a tick. **(3) Silent failure modes hid the regression**: a single unhandled rejection inside `setInterval(pollDeferredQueue, ...)` killed the loop with no observability beyond the absence of the `[PRESSURE_GUARD_WORKER] tick:` log line — impossible to alert on. Fix: every cadenced job now uses `safeInterval(name, fn, ms)` from `server/lib/safe-interval.ts` which wraps the callback in a top-level try/catch, increments `critsend_safe_interval_tick_errors_total{name=…}`, and records the last-success timestamp into the `critsend_safe_interval_last_tick_age_seconds{name=…}` gauge. The drain additionally heartbeats per-tick into `pressure_guard_leader.last_tick_at/last_tick_drained/last_tick_errors/last_tick_eligible` so the new admin-gated **GET `/api/admin/pressure-drain/health`** endpoint can answer "is the drain alive?" cross-process — returning `healthy`, `last_tick_age_s`, `leader_holder_id`, `leader_expires_in_s`, `deferred_pending_total`, `deferred_due_total`, `sends_5m` and structured `reasons.{lease_alive,tick_fresh,has_lease_row}`. Companion changes: counter-reconciler tick budget tightened from 30s → 5s (`COUNTER_RECONCILE_TICK_BUDGET_MS`) so a stalled reconcile query can no longer monopolise a pool slot for half a minute; new `server/workers/orphaned-sends-reconciler.ts` runs hourly in the worker process and force-fails `campaign_sends` rows stuck in `pending`/`attempting` whose parent campaign is already `completed`/`paused`/`cancelled` (counter `critsend_orphaned_sends_reconciled_total`). Health endpoint contract: returns rolling 5-min `drained_calls_5m` + `errors_5m` (computed from `campaign_sends` activity, not in-memory state) plus an error-rate guard (`PRESSURE_DRAIN_HEALTH_ERROR_THRESHOLD`, default 5) — `healthy=true` requires `lease_alive && tick_fresh && error_rate_ok`. Companion contract metric `critsend_pressure_drain_last_tick_age_seconds` (unlabelled) is published alongside the generic labelled `critsend_safe_interval_last_tick_age_seconds{name=…}` so existing alerting/dashboard queries can target the drain directly. Deploy hardening: `deploy/deploy.sh` now runs `pm2 reload all --update-env` (so every existing process picks up freshly-defined env vars) followed by an explicit `pm2 start ... --only critsend-drainer` (since `pm2 reload all` only touches processes the daemon already knows about — a brand-new app entry is silently skipped), and verifies every process emitted its canonical boot log line (`serving on port` / `[WORKER] Worker process starting` / `[DRAINER] Drainer process starting`) before exiting 0 — preventing the failure mode where a broken `dist/drainer-main.cjs` would deploy "successfully" while leaving the drain dead.

## Task #175 — Pressure-Guard Bootstrap on Neon PgBouncer (advisory-lock self-defeat)

Production incident 2026-05-22 10:02-10:11: drain went to **0 sends for 9 minutes** with no errors, no alerts, no obvious cause. Diagnostic on Neon DB found 3 system tables missing — `pressure_guard_leader`, `pressure_drain_tick_errors`, `pressure_maintenance_state` — even though their `CREATE TABLE IF NOT EXISTS` statements had shipped weeks earlier in `server/services/pressure-guard.ts`. The `verifyPressureSchemaReady()` check returned `has_maint_state=false`, the bootstrap stayed `deferred`, and the worker silently bailed on every drain tick before even reaching the leader-election logic. Manual `CREATE TABLE` on the Neon DB restored drain instantly (333 → 3308 sends/min over 90s).

**Root cause**: the entire essential-DDL block (lines 191-282 of the pre-fix `pressure-guard.ts`) was wrapped inside `withAdvisoryLock(LOCK_KEYS.PRESSURE_GUARD, …)` from `server/bootstrap-lock.ts`. That helper uses session-level `pg_try_advisory_lock` on a `pool.connect()` client — fundamentally **incompatible with Neon PgBouncer transaction pooling**. Each statement on the client is routed to a *different* upstream PG backend after PgBouncer's per-transaction recycling, so:

1. `SELECT pg_try_advisory_lock(900013)` ran on backend A and returned `acquired=true`.
2. The 22 subsequent `client.query()` calls (DDL + the eventual `pg_advisory_unlock`) all ran on rotating backends B/C/D/...Z. The lock stayed orphaned on backend A and survived in PgBouncer's pool indefinitely (until the physical connection died, which on Neon Launch can be hours-to-days).
3. Subsequent boots that grabbed a PgBouncer connection routed to backend A (or any other leaked-lock holder) got `acquired=false` and exited via the "Another process is running bootstrap — skipping" branch. The DDL never executed.
4. The `result === "ran" || result === "skipped"` readiness gate at the bottom treated `"skipped"` as a soft success path conditional on `schemaOk` — but `schemaOk` itself depended on tables that the skipped DDL was supposed to have created. Chicken-and-egg → permanent `deferred` state.

This is the **exact same failure mode** that the inline comment on line 209 of the same file (referring to `pressure_guard_leader`) called out as the reason for moving the *runtime* leader election off `pg_try_advisory_lock` onto a lease table — but the bootstrap that creates that lease table was itself still gated by the broken mechanism. The runtime fix could never engage because the schema it depended on couldn't be created.

**Fix (this task)**: hoist all essential DDL out of `withAdvisoryLock` into a new `ensurePressureGuardEssentialSchema()` helper that runs every statement directly via `pool.query()` (one PgBouncer transaction per statement, no session-level state). Every statement is `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE … ADD COLUMN IF NOT EXISTS` / `INSERT … ON CONFLICT DO NOTHING` / `CREATE INDEX IF NOT EXISTS` — PG serialises concurrent runners at the catalog level, so multiple processes booting at the same time is safe. Called unconditionally at the start of `runPressureGuardHeavyMaintenance()` before the lock wrapper. The advisory lock is retained around the heavy section (CONCURRENTLY index builds + `first_deferred_at` backfill) because that work is genuinely expensive and worth serialising — but the lock is now non-load-bearing: the readiness gate uses ONLY `schemaOk` (was `result === "ran" || schemaOk`), so a leaked PgBouncer lock can no longer permanently shut the drain.

**Architectural rule reinforced** (already in `replit.md` for the runtime path, now also applies to bootstrap): **any code that runs through Neon's pooled URL must avoid session-level PG state** — that includes `pg_try_advisory_lock`/`pg_advisory_unlock`, `SET LOCAL` outside a transaction, server-side prepared statements, and `LISTEN/NOTIFY`. Use lease-table patterns (atomic single-statement `INSERT … ON CONFLICT` with TTL), `pg_advisory_xact_lock` (auto-released at COMMIT), or run on the direct (non-pooled) Neon URL. The `bootstrap-lock.ts::withAdvisoryLock` helper itself is left in place for legacy callers but is now deprecated for new code paths through the pooled URL — callers should either be rewritten to use direct `pool.query()` (if the work is idempotent) or moved to a lease-table.

**Observability gap that allowed this to escape detection**: `verifyPressureSchemaReady()` returning false caused the worker to bail BEFORE writing any drain-tick log line. The `last_tick_at` heartbeat that powers `/api/admin/pressure-drain/health` was therefore stale-but-not-recent-enough-to-trip-alerts (the row simply didn't exist). Follow-up: alert on `pressure_drain_tick_errors` row count growth AND on `bootstrapState === "deferred"` exceeding 60s — neither of which currently exists.

## Task #173 — Pressure-Drain Head-of-Line Blocking Fix

The pressure-guard drain was running at **5.8% of its configured capacity** (~467 sends/min observed vs. an 8000/min ceiling from `DRAIN_PARALLELISM=4 × SMTP_CONCURRENCY=20 × ~100/sec/SMTP-conn`) despite Tasks #153/#154 having already parallelized both the drain-level and SMTP-level fan-out. Diagnostic (2026-05-22): 221k drainable rows across 45 active campaigns, but the eligibility query `SELECT DISTINCT campaign_id FROM campaign_sends … ORDER BY campaigns.created_at ASC LIMIT 20` picked the 20 OLDEST campaigns regardless of how much each actually had to drain — and the top-20 FIFO slice held only **9 ready_now rows total** while 200k+ rows on younger campaigns waited behind. Each tick's parallel-drain workers therefore burned the full 25s claim+finalize round-trip on near-empty queues, never reaching the campaigns where the batched SMTP fan-out would have amortized. Classic head-of-line blocking. **Fix has three layers:**

**(1) Slot capacity (Phase 1)**: `PRESSURE_GUARD_MAX_CAMPAIGNS` bumped 20 → 60 in all three PM2 env_production blocks (`critsend-web`, `critsend-worker`, `critsend-drainer`). The current production fleet is ~45 simultaneously-deferring campaigns; 60 gives the volume-priority ordering headroom to actually re-rank instead of always picking the same prefix.

**(2) Volume-priority eligibility query (Phase 2)**: the `SELECT DISTINCT` is replaced by a `WITH per_campaign AS (SELECT campaign_id, COUNT(*) AS drainable_count FROM campaign_sends WHERE … GROUP BY campaign_id) SELECT pc.campaign_id, c.created_at, pc.drainable_count, c.pending_count, c.sent_count FROM per_campaign pc JOIN campaigns c ON c.id = pc.campaign_id WHERE c.status IN ('sending','paused') ORDER BY pc.drainable_count DESC, c.created_at ASC NULLS FIRST LIMIT $1` with `LIMIT = MAX_CAMPAIGNS_PER_TICK × 2`. The COUNT is cheap because `campaign_sends_pressure_deferred_idx` covers the WHERE filter as a partial index. The `× 2` headroom lets the JS back-pressure filter drop some candidates without leaving slots empty. **Fairness slice** (`PRESSURE_GUARD_FAIRNESS_PCT`, default 20%): after the volume-priority ordering, the first `MAX × (100 - FAIRNESS_PCT)/100` campaigns are "volume picks"; the remaining `MAX × FAIRNESS_PCT/100` slots are filled from the candidates NOT in volume picks, re-sorted by `created_at ASC`. This guarantees a 3-day-old trickle still gets ≥ FAIRNESS_PCT of every tick's slots even when a fresh launch dominates `drainable_count`. Setting `PRESSURE_GUARD_FAIRNESS_PCT=0` reverts to pure volume priority; `=100` reverts to legacy pure FIFO.

**(3) Winding-down back-pressure (Phase 3)**: a campaign is flagged "winding_down" when `campaigns.pending_count < PRESSURE_GUARD_WINDING_DOWN_PENDING_MAX` (default 100) AND `drainable_count < PRESSURE_GUARD_WINDING_DOWN_DRAINABLE_MAX` (default 50) **continuously** for ≥ `PRESSURE_GUARD_WINDING_DOWN_PERSISTENCE_MS` (default 24h). The state is sticky (timestamp recorded on first match) but resets the instant either criterion stops holding, so a temporary trickle won't be permanently throttled. Winding-down campaigns are skipped if they were drained < `PRESSURE_GUARD_WINDING_DOWN_TICKS_GAP` (default 4) ticks ago — i.e. drained ~1 tick out of every 4, freeing the other 3 slots for younger campaigns with real backlog. State lives in two module-level `Map<campaignId, number>` in the worker process; process restart resets state harmlessly (re-derives over the next 24h of ticks). **Architectural rationale**: fully in-memory because (a) the state is purely advisory — the worst case of incorrect resets is a winding-down campaign drains one extra batch on the wrong tick (~1000 sends), no correctness impact; (b) avoiding extra DB roundtrips keeps the eligibility query under the 25s `statement_timeout`; (c) the dedicated drainer process (Task #160) is the only leader, so cross-process consistency is not a concern outside of leader-handoff windows (resolved by the same re-derivation logic).

**Observability**: tick log line now includes `picked=V+F, winding_down=N, back_pressured=M` so the head-of-line condition is grep-able. Two new Prometheus gauges: `critsend_pressure_guard_winding_down_campaigns` (currently flagged + persisted past 24h) and `critsend_pressure_guard_back_pressured_last_tick` (skipped on the most recent tick). The `back_pressured > 0 AND drained_calls < MAX_CAMPAIGNS_PER_TICK × 0.5` pattern in logs means fairness is actively unblocking younger campaigns. **Acceptance check**: per-minute send rate on a backlog of ~200k drainable rows should sit at 6k-8k sends/min (vs. the previous 467 sends/min plateau) within 2-3 ticks of deploying this change.

## Task #161 — Drain Tracking Parity

The pressure-guard drain worker (`server/workers/pressure-guard-worker.ts::drainCampaign`) previously initialised `trackingOpts = { trackOpens, trackClicks, linkMap: new Map() }` with a misleading "HMAC fallback" comment — but `addTrackingToHtml` (server/email-service.ts) needs **both** a populated `linkMap` AND a non-null `trackingDomain` (`baseUrl`) to rewrite hrefs and inject the open pixel. Without them, deferred-path emails went out as **raw HTML with direct `redirect.critads.com` links** → recipient clicks worked (client saw traffic) but Critsend recorded nothing — 0 pixel hits, 0 click rows. Constated on the 2026-05-14+ campaigns: every campaign with `deferred_count > 0` had its open rate drop from ~20% to **0% starting at the exact batch where the drainer took over** (Darel batch 6 / 13:06 UTC, F. Saget Mahle batch 7 / 13:33 UTC, F. Saget rndaserver batch 8 / 14:57 UTC, CFC batch 9, Zadig batch 4 — the cutover batch is always ≥4h after the previous one, marking the drainer handoff). The 2026-05-13 Eram campaign (185k sent, pre-pressure-rollout) had 28/28 batches at 24% with zero degradation — direct proof the bug is drainer-specific. F. Saget Mahle `f19f77d2` lost **~73% of its tracking** (64k subs tracked out of 235k). **Fix**: parity with the bulk sender hot-path (`campaign-sender.ts:386-419, 694-710`) — set `trackingDomain`/`openTrackingDomain` from the MTA, call `preregisterCampaignLinks` once per drain batch, then `batchCreateClickTokens` + `batchCreateUnsubscribeTokens` for the eligible winners. All three failure paths log a structured `[TRACKING_BREAK]` warning so any future regression is grep-able in prod logs (previously the bug was invisible: no error, no metric — just silent zeroes in `campaign_stats`). Defensive guard logs `[TRACKING_BREAK]` if `trackClicks=true` but `linkMap.size===0 && !mta.trackingDomain` at send time — that combination must never reach `sendEmailWithNullsink`. **Important contract**: `subscriberId` is set inside `sendEmail`/`sendEmailWithNullsink` per-call (not in the shared `trackingOpts`), so the same `trackingOpts` object is safe to reuse across the bounded-parallel SMTP fan-out workers. **Historical data is unrecoverable** — emails already left with the wrong HTML; only post-fix sends will be tracked correctly.

## Task #181 — Stuck-Pending Self-Heal

Production incident: ~20-30 campaigns sat for **hours to days** in `status='sending'` (or `'scheduled'`) without any user-facing pause reason and without the legacy `runCampaignGuardianPoll` rescuing them. Root-cause analysis surfaced **five** distinct stall patterns the old guardian (which only matched "sending with no active job in the last 2min") could not see. Steps 1-2 were operational (manual rescue + DB forensic queries on prod). Steps 3-7 are the code self-heal landed here.

**Diagnosis surface** (`server/services/stuck-campaign-diagnosis.ts`). Single read-only classifier shared between guardian + admin endpoint + Prometheus gauge so all three sources agree. Each campaign is classified at most once; branches are priority-ordered:
1. `scheduled_past_due_no_job` — `status='scheduled'` and `scheduled_at < NOW() - STUCK_SCHEDULED_MIN` (default 10min) with no pending/processing `campaign_jobs`. The scheduled-campaign poller missed it.
2. `sending_no_active_job` — legacy branch. `status='sending'` with no `pending`/`processing`/recently-`failed` (< STUCK_SENDING_NO_JOB_MIN, default 2min) job.
3. `sending_stale_heartbeat` — `status='sending'` with only a `processing` job whose `heartbeat` (or `started_at`) is older than STUCK_HEARTBEAT_STALE_MIN (default 5min). Worker is dead but `cleanupStaleJobs`' 30-min sweep hasn't fired yet. **Critical**: the legacy "no active job" branch never matched these because a `processing` row still satisfies "active" — campaigns could sit wedged for the full 30min window per worker death.
4. `sending_retry_budget_exceeded` — `status='sending'` with a `failed` job whose `retry_count >= STUCK_MAX_JOB_RETRIES` (default 10) and no successor. `handleJobError`/`handleJobCompletion` stop re-enqueuing once `retry_until` expires but leave the campaign in `sending` — invisible to operators. Now auto-pauses with `pause_reason='retry_budget_exceeded: <detail>'`.
5. `mid_flight_crash` — `status='sending'`, `started_at NOT NULL`, `campaign_sends` rows exist, but `max(sent_at) < NOW() - STUCK_NO_PROGRESS_MIN` (default 10min) AND no active/recent job. Ghost-sweep branch A only handled the `started_at IS NULL` pre-enumeration crash. This new branch handles a sender crashing mid-stream — sends partially written, no job alive to resume them.

**Guardian action map** (`runCampaignGuardianPoll`): `reenqueue` (1,2,5 — re-enqueue + NOTIFY; promotes scheduled→sending first), `fail_job_and_reenqueue` (3 — completeJob('failed', diagnosis) + enqueueCampaignJobWithRetry with bumped retry_count + 5s backoff), `pause_retry_budget_exceeded` (4 — sets `status='paused'` with the diagnostic detail truncated to 500 chars).

**Ghost-sweep parity** (`server/workers.ts::sweepGhostCampaigns`). Branch A unchanged. New branch B mirrors `mid_flight_crash` so whichever loop ticks first heals the campaign — defense in depth for the production incident. Never touches counters or `started_at`; the resume logic in `campaign-sender.ts` reconciles state from the existing `campaign_sends` rows.

**Operator surface**:
- `GET /api/admin/stuck-campaigns` (`server/routes/admin-stuck-campaigns.ts`) — admin-gated (same `requireAdmin` resolution order as `/api/admin/pressure-queue`: `users.is_admin` → `ADMIN_USER_IDS` env → dev fallback → fail-closed in prod). Returns thresholds, per-reason totals, full per-campaign diagnosis. Read-only; safe to poll.
- Prometheus gauge `critsend_campaigns_stuck_total{reason="..."}` (`server/metrics.ts`). Refreshed every guardian tick; **set unconditionally** including 0 for absent labels so dashboards don't retain stale non-zero readings. Labels match the `StuckReason` union exactly.
- Campaigns list UI (`client/src/pages/campaigns.tsx`) — `pause_reason` rendered inline under the status badge for `paused`/`failed` campaigns (truncated 180px + `title` tooltip). Failure dialog continues to show the full reason.

**Tunables** (all env-overridable with safe bounds; out-of-range → default): `STUCK_SCHEDULED_MIN=10`, `STUCK_SENDING_NO_JOB_MIN=2`, `STUCK_HEARTBEAT_STALE_MIN=5`, `STUCK_NO_PROGRESS_MIN=10`, `STUCK_MAX_JOB_RETRIES=10`.

**Regression coverage** — `tests/stuck-campaign-diagnosis.test.ts` seeds one campaign per stuck pattern (plus a healthy control with fresh heartbeat) and asserts each gets the correct `reason`/`action`, that the control is never flagged, and that classifications are mutually exclusive (no campaign appears in two branches).

## Tracking — Single Chokepoint (`prepareTrackedHtml`), Pretty/Disguised URLs, Lifecycle-Stage & FBL Invariants

- **Tracking:** Implements open tracking (1x1 pixel) and click tracking (redirects with open-redirect prevention). All tracking URLs are HMAC-SHA256 signed. **Single chokepoint invariant (Task #185):** every outbound email path — bulk campaign sender, pressure-guard drain worker, automation engine, Resend fallback, and (opt-in) test sends — funnels through `prepareTrackedHtml` in `server/email-service.ts`. That helper is the only place that runs `personalize → image rewrite → unsubscribe URL resolution → tracking pixel + click rewriting → footer`. Adding a new send path? Use this helper or your emails will silently lose tracking — there's a guard test in `tests/prepare-tracked-html.test.ts` that asserts the pixel is injected and raw `<a href>` URLs are rewritten. Test sends default to **no** tracking (untracked preview) but accept an explicit `trackInTest: true` opt-in; the opt-in requires a saved `campaignId` (and looks up the recipient by email, or accepts an explicit `subscriberId`) so the tracking events can satisfy the `campaign_stats` / `campaign_sends` FK constraints. Automation `send_email` steps lazy-create one synthetic `campaigns` row per workflow (status `automation_internal`, hidden from `getCampaignsPaginated`) cached on `automation_workflows.tracking_campaign_id` so opens/clicks generated by automation are persistable. Captures enriched context (IP, country, device, browser, OS) and uses a link registry for opaque UUID tokens in tracking links, along with branded short tracking URLs. **Pretty/disguised URLs (send-time rewrite, default ON):** to stop URLs from advertising marketing/tracking intent to anti-spam content scanners, the send-time pipeline rewrites two URL families inside `prepareTrackedHtml` only — already-sent emails are untouched and the legacy serving routes stay registered forever. (1) Campaign **images**: stored relative `/campaigns/{yr}/{mo}/{id}/{file}` → emitted as `${domain}/i/...` (`rewriteImageUrls` in `server/email-service.ts`; `/i/` route aliases the `/campaigns/` image handler in `server/routes.ts`). (2) **Open pixel**: legacy `${base}/api/track/open/{campaignId}/{subscriberId}?sig=&mid=` → disguised as a static image `${base}/o/{campaignId}/{subscriberId}/p.gif?sig=&mid=` (`generateSignedOpenTrackingUrl(...,pretty)` in `server/tracking.ts`; the `/o/:campaignId/:subscriberId/:file` route shares the EXACT same handler as `/api/track/open/` in `server/routes/tracking.ts` — `p.gif` is cosmetic/ignored, sig+mid stay query params so HMAC verification is identical). Clicks (`/c/{token}`) and unsubscribe (`/u/{token}`) were already pretty. Toggle: `prettyTrackingUrlsEnabled()` = `process.env.PRETTY_TRACKING_URLS !== "false"` — set `PRETTY_TRACKING_URLS=false` to revert NEW sends to legacy paths (kill-switch, no code change). Both low-level helpers default to this env flag (override via the `prettyUrls` option/param), so every send path (bulk, drain, automation, Resend, test) gets pretty automatically. Guard tests: `tests/pretty-urls.test.ts` (pretty default + legacy fallback + explicit override) and the existing `tests/prepare-tracked-html.test.ts` (already `/o/`-and-`/api/track/open/`-agnostic). Tracking events are buffered in-memory and flushed in batched multi-row inserts to a dedicated `pg.Pool` for isolation. Engagement counters are cached on the `campaigns` table and a 15-min counter-drift reconciler (`server/workers/counter-reconciler.ts`) ensures data consistency. **Lifecycle stage invariant (2026-06-01):** the stage that reconciles `campaigns.{pending_count, deferred_count, failed_count}` runs FIRST and MUST gate off the tiny `campaigns` table (sending/paused or recently started/completed), then count each campaign's pending/failed rows via a per-campaign `CROSS JOIN LATERAL` on `campaign_sends_campaign_status_idx (campaign_id, status)` — NEVER aggregate `campaign_sends` filtered by `campaign_id IN (recent_campaigns)`, which makes the planner parallel-seq-scan the whole ~89M-row table and blows the 5s tick budget (this caused ~30× deferred_count drift). `deferred_count` reconciles to "held" = `status='pending' AND eligible_at IS NOT NULL` (matches the live counter, which decrements on send, NOT when `eligible_at` passes — do not revert to `eligible_at > NOW()`). Later stages (sent_count over ~89M sent rows, engagement over `campaign_stats`) may still exhaust the budget and abort; that is tolerated because lifecycle commits first and is the UX-critical path. **FBL complaints are treated as plain unsubscribes on the subscriber side**: the campaign's standard unsubscribeTag is added (no `STOP-` prefix, no 7-day `suppressed_until` window) so existing segment exclusions naturally drop complainers. Campaign-level `complaints_count` and per-event `campaign_stats(type='complaint')` rows continue to be recorded so deliverability dashboards still distinguish complaints from unsubscribes. Pre-existing historical `STOP-*` tags on subscribers are preserved (no migration).

## Job Queues — Sender FIFO + Aged-Job Fairness Tie-Breaker

- **Job Queues:** Dual-mode system with PostgreSQL-backed queues (SKIP LOCKED and LISTEN/NOTIFY) and optional BullMQ + Redis for advanced features. The campaign **sender** claim (`claimNextJob` in `server/repositories/job-repository.ts`) is FIFO by `campaigns.created_at`, but with an **aged-job fairness tie-breaker**: any job pending longer than `JOB_FAIRNESS_PROMOTE_MIN` minutes (default 15) is promoted ahead of the created_at FIFO. This prevents an old, perpetually-re-enqueuing campaign from starving requeued/younger campaigns (a freshly re-enqueued job is not aged, so it can't preempt a long-waiting one). This is independent from the pressure-guard **drain** FIFO. Never mutate `campaigns.created_at` to reprioritize — it is the immutable launch-ancestry key both the sender FIFO and the drain's deferred-subscriber serialization depend on.

## Maintenance — `tracking_tokens` Daily-Partitioned Retention + One-Time Migration (cutover 2026-06-01, legacy dropped 2026-06-04)

- **Maintenance — `tracking_tokens` daily retention (partitioned):** `tracking_tokens` is a **daily RANGE-partitioned table on `created_at`** (partition key forces composite PK `(token, created_at)` — token uniqueness is intentionally NOT enforced; the rare cross-day token collision is accepted as noise and resolution is made deterministic via `ORDER BY created_at DESC LIMIT 1`, a backward PK index scan). Partitions are named `tracking_tokens_pYYYYMMDD` (UTC days). Helper module: `server/tracking-partitions.ts` (`ensureTrackingTokenPartitions`, `dropExpiredTrackingTokenPartitions`, `isTrackingTokensPartitioned`, `buildPartitionedTableDDL`). Retention runs once a day at **01:00 Europe/Paris** via `scheduleDailyTrackingTokenPurge` in `server/workers.ts`: it **DROPs** whole day-partitions older than `TRACKING_TOKEN_RETENTION_DAYS` (default 90; prod 7) — instant, reclaims storage immediately, zero WAL bloat — and tops up a 7-day forward buffer of partitions so live inserts never hit a missing partition. **Pre-migration fallback:** if the table is still non-partitioned (`isTrackingTokensPartitioned` false), the job falls back to the old batched DELETE (`TRACKING_TOKEN_MAX_DELETE_PER_RUN`, default 5M). Multi-process safety (unchanged): all 3 PM2 processes arm a 01:00 timer but a `db_maintenance_logs` 23h gate lets only the first run; each run writes a `triggered_by='daily_1am_paris'` row. **drizzle-kit push is shielded** from this table via `tablesFilter: ["!tracking_tokens", "!tracking_tokens_*"]` in `drizzle.config.ts` (the partitioned layout is raw-SQL managed by the bootstrap DDL in `campaign-repository.ts`, NOT by Drizzle migrations) — never remove that filter or `deploy/deploy.sh`'s `drizzle-kit push --force` will rewrite the table. **One-time migration** (single→partitioned) is performed by `scripts/migrate-tracking-tokens-partitioning.ts` (`status|prepare|swap|copy|verify|drop-legacy`): it creates an empty partitioned `tracking_tokens_new`, transactionally renames old→`tracking_tokens_legacy` and new→`tracking_tokens`, copies the last N days (keyset on `(created_at, token)`, `ON CONFLICT DO NOTHING`), then drops legacy. During the window between swap and drop-legacy, **zero tracking loss** is guaranteed by a dual-read fallback: token resolution (`server/tracking-queries.ts` hot path + `resolveTrackingToken` in `campaign-repository.ts`) falls back to `tracking_tokens_legacy` on a miss and self-disables on `42P01` once legacy is dropped. **Prod cutover (2026-06-01) → legacy DROPPED (2026-06-04):** `prepare`+`swap` ran on 2026-06-01 (table partitioned; pre-swap data parked in `tracking_tokens_legacy`; dual-read active). The bulk `copy` of the recent window was **deliberately skipped**. On **2026-06-04** the operator chose to **`DROP TABLE tracking_tokens_legacy` immediately** — only 3 days post-swap, NOT the planned 7 — **explicitly accepting** that click/unsubscribe short links (`/c/:token`, `/u/:token`) from emails in the pre-swap tail **2026-05-28 → 2026-06-01** now return `404` (those tokens lived only in legacy and were still inside the 7-day window). **Opens are unaffected** — the open pixel (`/api/track/open/:campaignId/:subscriberId`) uses HMAC-signed campaign/subscriber IDs, not tokens — and **all already-recorded stats are untouched** (`campaign_stats` rows + `campaigns` counters are separate tables). Reclaimed ~284 GB (DB **391 GB → 107 GB**). The dual-read fallback (`server/tracking-queries.ts` hot path + `resolveTrackingToken` in `campaign-repository.ts`) self-disables on the first `42P01` at runtime — **no deploy required**. Going forward retention is **partition-drop only** at **7 days** (`TRACKING_TOKEN_RETENTION_DAYS=7`); legacy is gone, so the old `drop-legacy` step / hard-gate are now historical.

## Robustness — Auto-Resume (web + worker), Force-Resume Backstop, Guardians

- **Robustness:** Includes graceful shutdown, memory monitoring with load shedding, automated campaign auto-resume (MTA down + DB connection errors), bounce webhook idempotency, and bulk-optimized batch webhook processing. **Auto-resume runs in BOTH the worker AND the always-up web process** (`startMtaRecoveryChecker` in `server/workers.ts`, wired into the web-process startup block in `server/index.ts`) so a crash-looping worker can no longer leave campaigns stuck in `paused/mta_down`. Resume uses a guarded conditional flip (`resumeCampaignAtomic`: `UPDATE campaigns SET status='sending', pause_reason=NULL WHERE status='paused' AND pause_reason=$reason RETURNING id`) so concurrent web+worker checkers resume exactly once (only the row-winner clears stuck jobs + enqueues + invalidates the list cache). A bounded **force-resume backstop** (`MTA_FORCE_RESUME_AFTER_MS`, default 15min, validated finite ≥60s) resumes a campaign even if SMTP `verify()` keeps failing (the probe can lie while real sends would succeed); a genuinely-down MTA simply re-pauses, so worst case is a bounded periodic retry, not a tight loop. `campaigns` has no `paused_at`, so the timer is an in-memory per-campaign Map that self-prunes when a campaign leaves the paused list. Web-process guardians rescue stuck import and campaign jobs. Startup bootstrap migrations use advisory locks and `CREATE INDEX CONCURRENTLY` for safety. Transient DB errors during campaign sending are re-thrown to the job-level handler which requeues with exponential backoff instead of permanently pausing campaigns.

## PMTA Queue Monitoring (Task #193)

- **PMTA Queue Monitoring (Task #193):** Background collector in `server/services/pmta-collector.ts` SSHes into the PMTA 4.5 host every 5 minutes (`PMTA_COLLECTOR_INTERVAL_MS`, default 300s) and runs `pmta show queue <domain>` for each domain in `PMTA_DOMAINS` (comma-separated, validated against `/^[a-z0-9.-]+$/i` to prevent shell injection). The parser extracts a pending count from PMTA summary lines (`Total messages`, `kmsg`, `N messages queued`, falling back to recipient-like row count) and greps for the regex `\b(error|timeout|refused|blocked|defer|421|450|451|452|550|554)\b` to surface error lines. One snapshot row per (domain, tick) is persisted to `pmta_queue_snapshots`. **Architectural rule (repeated here because it has bitten us twice — pressure-guard drain and now this):** singleton scheduling across the 3 PM2 processes uses a lease-table leader election (`pmta_collector_leader`), NEVER `pg_try_advisory_lock` (leaks on Neon's PgBouncer transaction pooling). **HTTP contract:** `GET /api/pmta/snapshots/latest` and `GET /api/pmta/snapshots/:domain/history` serve cached rows only — they NEVER open an SSH connection on the request path. `POST /api/pmta/refresh` (rate-limited 6/min) triggers an immediate forced tick. Required secrets: `PMTA_SSH_HOST`, `PMTA_SSH_PORT` (default 22), `PMTA_SSH_USER`, `PMTA_SSH_PRIVATE_KEY` (raw PEM, never logged), `PMTA_DOMAINS`. Frontend page at `/pmta` (TanStack Query, 30s polling) shows pending count, error count, status badge per domain, and a drawer with matched error lines + raw output excerpt. Parser regression coverage in `tests/pmta-parser.test.ts`.

## Object Storage for CSV Imports — Hetzner S3, Throttle Hardening, Deferred Upload to Worker

- **Object Storage for CSV imports:** Selected via `STORAGE_BACKEND` env var. Production runs on `hetzner` (Hetzner Object Storage, S3-compatible) to eliminate "CSV file not found" errors that occurred with local-disk storage when files disappeared between upload and worker pickup. Required env vars: `HETZNER_S3_{ENDPOINT,REGION,BUCKET,ACCESS_KEY,SECRET_KEY}`. Activation guide: `deploy/HETZNER_S3_SETUP.md`. Implementation in `server/storage-backends/hetzner-s3.ts` (multipart uploads, bounded timeouts, typed errors — `ObjectStorageAccessError` / `ObjectStorageTransientError` / NotFound — so the requeue route can distinguish "user must re-upload" from "operator must fix env/IAM" from "client should retry"). **Throttle hardening (2026-05-31):** Hetzner returns `503 SlowDown` under bursts of concurrent multipart PUTs, which crashed *every* import at once. Two-layer fix:
1. **Backend retry** (`server/storage-backends/hetzner-s3.ts`): S3Client `retryMode: "adaptive"` (client-side rate limiter for throttle storms) + `maxAttempts` raised 4→8, plus a `withTransientRetry` wrapper on every op that retries ONLY `ObjectStorageTransientError` with bounded exponential backoff+jitter (the upload op recreates the read stream each round; consumed streams can't replay). Tunables: `HETZNER_S3_{MAX_ATTEMPTS,RETRY_ROUNDS,RETRY_BASE_MS,RETRY_MAX_MS}`. Factory in `server/storage-backends/index.ts`.
2. **Deferred upload to worker (2026-05-31):** the original synchronous-request-path upload (`POST /api/import` + chunked-complete handler) had no requeue path, so a transient 503 past the backend retries permanently `failed` the job ("Import setup failed" → later "CSV file not found, re-upload") and a sustained storm risked pushing handler latency past the proxy timeout. Now both entry points only persist the file to the local staging volume and enqueue the queue row pointing at the **local** path (returning 202 immediately); the object-storage upload runs as the **first step of the worker job** via `ensureCsvUploadedToObjectStorage` in `server/services/import-processor.ts` (upload → verify with `objectExists` → atomically rewrite `import_job_queue.csv_file_path` to `/objects/...` → unlink local temp). It is idempotent (no-op for `phase2_merge`, already-`/objects/` paths, and the local-disk backend) so requeue/recovery re-entry is safe. On `ObjectStorageTransientError` the worker `.catch` requeues via `requeueImportJobForRetry(queueId, WORKER_ID)` instead of failing, bounded by a **wall-clock** window (`IMPORT_UPLOAD_MAX_RETRY_MS`, default 2h, from `created_at`). Correctness rules: the requeue is **lease-bound** (`AND worker_id = WORKER_ID`, returns boolean — if `recoverStuckImportJobs` already re-claimed a >10-min-stalled upload, it matches 0 rows and the caller must NOT fail the job); it deliberately does **NOT** touch `retry_count` (owned by `recoverStuckImportJobs`, which hard-fails a stuck `processing` row at `retry_count >= 2` — sharing it caused premature failure during storms); and a terminal failure deterministically unlinks the orphaned local staging file. Valid because `critsend-web`/`worker`/`drainer` are separate PM2 processes on one VM sharing a persistent `IMPORT_UPLOAD_DIR` volume. (`server/services/import-worker.ts` is dead code; the active processor is `import-processor.ts` driven by `server/workers.ts`.) Residual risk: no periodic sweeper for files orphaned by a crash mid-upload. Fallback options: `local` (writes to `IMPORT_UPLOAD_DIR`) and `replit` (Replit App Storage, Replit deployments only).

## Import DB Connection-Acquire Retry — 3 Layers (2026-06-01)

- **Import DB connection-acquire retry (2026-06-01):** The import processor's batch concurrency previously equalled the import pool size (`MAX_INFLIGHT === IMPORT_POOL_MAX`), so N concurrent COPY/INSERT batches held all N connections with zero headroom; the start-of-wave burst of `pool.connect()`s against Neon's PgBouncer pooled endpoint could exceed `connectionTimeoutMillis` and throw "timeout exceeded when trying to connect" — with no retry, one batch's blip set `batchError` and failed the ENTIRE import, and the same blips on per-row fallbacks (`singleUpsert`) permanently marked rows `failed` (observed: an 80k-row CSV failed twice, then "completed" with ~2,700 failed). Fix: `server/services/conn-retry.ts` (`isTransientConnError`, `withConnRetry` — bounded expo backoff + jitter, retries ONLY connection-class errors: connect-timeout/`08xxx`/`57P01`/ECONN*/EPIPE, never SQL/data errors). Retry is applied at **three layers**, all retrying ONLY connection-class errors:
1. **Dedicated import pool** (`server/services/import-processor.ts`): `connectWithRetry()` wraps every `pool.connect()`, `queryWithRetry()` wraps every `pool.query()`, and `execWithRetry()` wraps every importDb `db.execute()` (GIN `DROP INDEX IF EXISTS`, `DELETE FROM import_staging`, the two `import_job_queue` path/status rewrites — all idempotent). Plus `MAX_INFLIGHT = max(1, CONCURRENCY-1)` (1 connection of headroom) and `import-pool.ts` `connectionTimeoutMillis` 15s→30s (env `IMPORT_POOL_CONNECT_TIMEOUT_MS`).
2. **Shared MAIN pool — the critical missing piece (2026-06-01, second pass):** a dedicated import pool alone could NOT fix it because the import job's metadata / heartbeat / progress / status / finalization writes ALL run on the shared MAIN pool (worker pool, aggressive ~2s `connectionTimeoutMillis` in `server/db.ts`), NOT the import pool. A brief main-pool checkout-timeout under worker load failed the whole import and got attributed to the job (the symptom users kept hitting after the first pass). Fix: `import-processor.ts` imports `storage as rawStorage` and exposes a **retrying `storage` Proxy** — EVERY `storage.*` call in the module (~46: `getImportQueueItem`/`getImportJob`/`updateImportJob`/`updateImportQueue{Heartbeat,Progress,ProgressWithCheckpoint}`/`detectImportRefs`/`areGinIndexesPresent`/`logError`/finalization) auto-retries connection-class blips. `this` is bound to rawStorage so a method's internal `this.xxx()` hits raw storage (no proxy recursion / double-retry). New import-path storage calls are protected automatically.
3. **Poller** (`server/workers.ts` `pollForImportJobs`): `claimNextImportJob` / `recoverStuckImportJobs` / `cleanupStaleImportJobs` wrapped in `withConnRetry` (a connect blip there means a pending import never starts that tick).
Retry tunables: `IMPORT_CONNECT_{MAX_RETRIES,RETRY_BASE_MS,RETRY_MAX_MS}`. **Retry-safety:** all import writes use ABSOLUTE values (set status, set committedRows/newSubscribers totals — never increments), reads are pure, DML is idempotent (`ON CONFLICT` upserts, set-difference updates, LIMIT-loop deletes), so retry-after-reset can't double-apply. Coverage: `tests/conn-retry.test.ts`. **The ONE exclusion — `recreateSubscriberGinIndexes` (`CREATE INDEX CONCURRENTLY`)** is on `NON_RETRYABLE_STORAGE_METHODS`: a mid-flight reset leaves an INVALID index a blind retry collides with; it runs best-effort in its own try/catch and whole-phase failures are recovered by `recoverStuckImportJobs`. Any NEW non-idempotent / CONCURRENTLY-DDL storage method on the import path MUST be added to that denylist. (`logError` is left retryable on purpose — a duplicate error row beats losing the record in a storm.)
