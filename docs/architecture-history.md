## Task #148 — 503 Attribution

Every `503 service_busy` response funnels through `server/middleware/service-busy.ts` (`emitServiceBusy` / `recordServiceBusy`). One structured `[503]` log line per emission (with rid/method/path/route/source/kind/code/pool active+idle+total+waiting+saturation/lease — guaranteed per-request attribution from logs alone) + a 50-event in-memory ring buffer + the cross-cutting `critsend_service_busy_503_total{source,route}` counter make every emission attributable. Sources: `load_shed`, `lease_exceeded`, `checkout_timeout` (incl. `kind=upgraded_from_500` from the `poolErrorResponseUpgrade` patch), `handler_transient` (route-level transient DB error), `memory_pressure` (POST `/campaigns/:id/send`). Triage endpoint: **GET `/api/admin/503-attribution`** (admin-gated via `users.is_admin`/`ADMIN_USER_IDS`) returns total + per-source + per-route + per-pair counts plus the most-recent ring entries with rid, route, pool snapshot and lease holding. Frontend `apiRequest` now throws `ApiError` (with `.status` + parsed `.body`); the `/campaigns` page recognises 503 service_busy and shows a soft "Serveur momentanément occupé — Nouvelle tentative…" panel instead of the red error banner. The counter-reconciler push-downs the `recent_campaigns` filter INTO each `truth` CTE so each tick scans the active subset (~100 campaigns) instead of the full 20 M-row `campaign_stats` table — eliminating the recurring `statement_timeout` ticks that previously consumed a pool slot for 120 s. POST `/api/campaigns` validates `segmentId` + `excludeSegmentId` in a single `WHERE id = ANY(...)` round-trip so the route stays under the 2-checkout-per-request lease cap.

## Task #154 — Pressure-Guard SMTP Fan-Out

During the same 2026-05-14 prod incident the parallelized drain (Task #153) was confirmed running with `drained_calls=9` per tick, but cumulative throughput plateaued at ~800-3500 sends/min — far below the 24k/min projection. Root-cause: inside `drainCampaign`, the SMTP dispatch loop was **strictly sequential** (`for (const sub of eligibleSubs) { await sendEmailWithNullsink(...) }`), so each send waited for the previous SMTP RTT (~100ms) before starting the next. Per-campaign ceiling = ~10 sends/sec, × DRAIN_PARALLELISM=4 = ~2,400/min — exactly the observed rate. **Fix**: bounded-parallel SMTP fan-out inside `drainCampaign` using the same worker-pool pattern as Task #153 but at the per-send level. N workers (default `PRESSURE_GUARD_SMTP_CONCURRENCY=20`, hard-capped at 100) pull from a shared `sendQueue` of eligible subscribers; SMTP I/O is interleaved while Node's single-threaded event loop keeps `successIds`/`failedIds`.push race-free between awaits. With DRAIN_PARALLELISM=4 × SMTP_CONCURRENCY=20 the theoretical cluster-wide ceiling becomes ~80 simultaneous SMTP sends → ~24k sends/min. Peak fan-out is bounded by the Nodemailer pool per MTA (typically 5-10 conn × 7 MTAs = 35-70 sockets) so the 80 cap fits comfortably. The env var is persisted in both `critsend-web` and `critsend-worker` env_production blocks of `deploy/ecosystem.config.cjs`. Startup log line now includes `smtp-concurrency=N`. Diagnostic note: the previous bottleneck was invisible in the standard tick log (`drained_calls=N` counts `drainCampaign` invocations, not actual SMTP sends), so the symptom was "drain looks healthy but backlog grows" — only the per-MTA `recent_sent` query revealed the throughput plateau. Companion lesson: if the deferred queue starts to grow despite `leader_acquired=Y` and non-zero `drained_calls`, check the actual sends/min via `SELECT date_trunc('minute', sent_at), COUNT(*) FROM campaign_sends WHERE sent_at > NOW() - INTERVAL '10 min' AND status='sent' GROUP BY 1` before assuming the drain is broken.

## Task #153 — Pressure-Guard Drain Parallelization

The pressure-guard deferred-drain worker (server/workers/pressure-guard-worker.ts) previously processed eligible campaigns strictly sequentially — `for (const row of campaignsRes.rows) { await drainCampaign(...) }` — which capped per-tick throughput at ~1 campaign × BATCH rows / drain-duration. Constated during the 2026-05-14 prod incident: 10+ massive campaigns launched in parallel at 12:32-12:34 UTC on overlapping audiences pushed 810k rows into the deferred queue (321k immediately `due_now`, 488k still inside the 6h pressure window), but the sequential drain produced only ~1500 sends/min total — projected ~3-4 hours to drain. **Fix**: bounded-parallel drain with a fixed concurrency cap. The drain loop now spawns N workers (default `PRESSURE_GUARD_DRAIN_PARALLELISM=1`, prod set to 4 via deploy/ecosystem.config.cjs) that pull from a shared queue of eligible campaign IDs. Each `drainCampaign(campaignId)` call peaks at ~2 main-pool connections (claim txn + finalize txn; SMTP send is external I/O), so DRAIN_PARALLELISM=4 holds peak DB footprint at ~8 connections — well within the 30-slot main pool. JS single-threaded execution makes the `drainedCalls`/`errorCount` shared counter increments race-free despite interleaved awaits. The cap is hard-clamped to 16 to prevent runaway pool saturation if misconfigured. Companion change: deploy/ecosystem.config.cjs now persists the production-tuned drain knobs (`PRESSURE_GUARD_POLL_MS=10000`, `PRESSURE_GUARD_BATCH=1000`, `PRESSURE_GUARD_MAX_CAMPAIGNS=20`, `PRESSURE_GUARD_DRAIN_PARALLELISM=4`) into both `critsend-web` and `critsend-worker` env_production blocks so they survive `pm2 reload` / restart cycles (previously the same values were applied via one-shot `pm2 restart all --update-env` which is lost on the next ecosystem reload). All four are dotenvVars-overridable, so `.env` still wins for ad-hoc tuning. The "Starting" log line now includes `drain-parallelism=N` so per-process configuration is grepable. **Architectural note**: the drain is started from BOTH the web (DISABLE_WORKERS branch in server/index.ts) AND the worker process; only one acquires the leader lease at a time (Task #149 lease table), so the env vars MUST match on both sides — they do, via the shared dotenvVars+default mechanism.

## Task #152 — Bootstrap Lock Self-Heal

At every web/worker process boot, `releaseStuckBootstrapLocks()` (server/bootstrap-lock-recovery.ts) preemptively `pg_terminate_backend`s any idle PgBouncer-labelled backend (`application_name='pgbouncer'`, `state IN ('idle','idle in transaction','idle in transaction (aborted)')`) still holding a session-level advisory lock in our reserved bootstrap range (objids 900001-900020). This neutralises the Neon-PgBouncer transaction-pooling leak that `withAdvisoryLock` (server/bootstrap-lock.ts) suffers from on every `pm2 reload`: the previous process's `pg_try_advisory_lock(<objid>)` lands on backend X via PgBouncer, the Node process exits, but PgBouncer keeps backend X alive (idle) and the session lock leaks indefinitely — the next process boots, tries `pg_try_advisory_lock` on a different backend, gets `acquired=false`, logs "Another process is running bootstrap — skipping" and bails, so the bootstrap DDL never runs on the new code. Without this self-heal, Task #149's deploy hung in production with `pressure_guard_leader` table never created and `bootstrap=pending → deferred` looping every 15s for 6+ minutes until manual `pg_terminate_backend` via psql freed the leaked PIDs (constated 16564/16571/16609 holding objids 900004/900005/900015). The self-heal SQL is identical to `POST /api/admin/pressure-guard/release-stuck-locks` (still kept as a manual one-shot escape hatch, but no longer needed during normal deploys) but generalised to the full 900001-900020 range and called automatically. Best-effort: never throws, 5s `statement_timeout`, terminates only `application_name='pgbouncer'` idle backends so direct app connections are never touched. Logs `[LOCK_RECOVERY] (web-boot|worker-boot) terminated N leaked PgBouncer backends … by_objid={…}` on every boot for observability.

## Task #160 — Drain Process Isolation & Bulletproof Deploy

The 2026-05-15 prod incident (1h30 user-facing freeze) had three root causes that this task addresses together. **(1) Snowball ratio frozen on cumulative counters**: the sender's auto-throttle read `processed = campaigns.sent_count + failed_count` (incrementally maintained, drift-prone). When the drift desynced from the real-time deferred backlog, the ratio plateaued at 0.801 and the sender slept forever in the throttle branch even after the drain had emptied the queue. Fix: both numerator and denominator now come from a single `COUNT(*) FILTER (...)` over `campaign_sends`, with a 30s in-memory per-campaign cache (`PRESSURE_RATIO_CACHE_TTL_MS`) to keep per-iteration cost bounded. **(2) Drain process competing with web/worker for resources**: the embedded drain in both `server/index.ts` (DISABLE_WORKERS branch) and `server/workers.ts` shared the main DB pool with HTTP requests and import processing — a stalled query in either could starve the drain via pool saturation. Fix: a new dedicated `critsend-drainer` PM2 process (`server/drainer-main.ts` → `dist/drainer-main.cjs`) runs ONLY the pressure-guard worker with its own `DRAINER_PG_POOL_MAX=6` pool and `PROCESS_TYPE=drainer` (recognised in `server/connection-budget.ts`). The embedded drain is skipped on web/worker when `DRAIN_PROCESS_DEDICATED=true` (default in production via `deploy/ecosystem.config.cjs`); the existing leader-lease (`pressure_guard_leader` table) still keeps things safe during a partial rollout — only one process drains a tick. **(3) Silent failure modes hid the regression**: a single unhandled rejection inside `setInterval(pollDeferredQueue, ...)` killed the loop with no observability beyond the absence of the `[PRESSURE_GUARD_WORKER] tick:` log line — impossible to alert on. Fix: every cadenced job now uses `safeInterval(name, fn, ms)` from `server/lib/safe-interval.ts` which wraps the callback in a top-level try/catch, increments `critsend_safe_interval_tick_errors_total{name=…}`, and records the last-success timestamp into the `critsend_safe_interval_last_tick_age_seconds{name=…}` gauge. The drain additionally heartbeats per-tick into `pressure_guard_leader.last_tick_at/last_tick_drained/last_tick_errors/last_tick_eligible` so the new admin-gated **GET `/api/admin/pressure-drain/health`** endpoint can answer "is the drain alive?" cross-process — returning `healthy`, `last_tick_age_s`, `leader_holder_id`, `leader_expires_in_s`, `deferred_pending_total`, `deferred_due_total`, `sends_5m` and structured `reasons.{lease_alive,tick_fresh,has_lease_row}`. Companion changes: counter-reconciler tick budget tightened from 30s → 5s (`COUNTER_RECONCILE_TICK_BUDGET_MS`) so a stalled reconcile query can no longer monopolise a pool slot for half a minute; new `server/workers/orphaned-sends-reconciler.ts` runs hourly in the worker process and force-fails `campaign_sends` rows stuck in `pending`/`attempting` whose parent campaign is already `completed`/`paused`/`cancelled` (counter `critsend_orphaned_sends_reconciled_total`). Health endpoint contract: returns rolling 5-min `drained_calls_5m` + `errors_5m` (computed from `campaign_sends` activity, not in-memory state) plus an error-rate guard (`PRESSURE_DRAIN_HEALTH_ERROR_THRESHOLD`, default 5) — `healthy=true` requires `lease_alive && tick_fresh && error_rate_ok`. Companion contract metric `critsend_pressure_drain_last_tick_age_seconds` (unlabelled) is published alongside the generic labelled `critsend_safe_interval_last_tick_age_seconds{name=…}` so existing alerting/dashboard queries can target the drain directly. Deploy hardening: `deploy/deploy.sh` now runs `pm2 reload all --update-env` (so every existing process picks up freshly-defined env vars) followed by an explicit `pm2 start ... --only critsend-drainer` (since `pm2 reload all` only touches processes the daemon already knows about — a brand-new app entry is silently skipped), and verifies every process emitted its canonical boot log line (`serving on port` / `[WORKER] Worker process starting` / `[DRAINER] Drainer process starting`) before exiting 0 — preventing the failure mode where a broken `dist/drainer-main.cjs` would deploy "successfully" while leaving the drain dead.

## Task #161 — Drain Tracking Parity

The pressure-guard drain worker (`server/workers/pressure-guard-worker.ts::drainCampaign`) previously initialised `trackingOpts = { trackOpens, trackClicks, linkMap: new Map() }` with a misleading "HMAC fallback" comment — but `addTrackingToHtml` (server/email-service.ts) needs **both** a populated `linkMap` AND a non-null `trackingDomain` (`baseUrl`) to rewrite hrefs and inject the open pixel. Without them, deferred-path emails went out as **raw HTML with direct `redirect.critads.com` links** → recipient clicks worked (client saw traffic) but Critsend recorded nothing — 0 pixel hits, 0 click rows. Constated on the 2026-05-14+ campaigns: every campaign with `deferred_count > 0` had its open rate drop from ~20% to **0% starting at the exact batch where the drainer took over** (Darel batch 6 / 13:06 UTC, F. Saget Mahle batch 7 / 13:33 UTC, F. Saget rndaserver batch 8 / 14:57 UTC, CFC batch 9, Zadig batch 4 — the cutover batch is always ≥4h after the previous one, marking the drainer handoff). The 2026-05-13 Eram campaign (185k sent, pre-pressure-rollout) had 28/28 batches at 24% with zero degradation — direct proof the bug is drainer-specific. F. Saget Mahle `f19f77d2` lost **~73% of its tracking** (64k subs tracked out of 235k). **Fix**: parity with the bulk sender hot-path (`campaign-sender.ts:386-419, 694-710`) — set `trackingDomain`/`openTrackingDomain` from the MTA, call `preregisterCampaignLinks` once per drain batch, then `batchCreateClickTokens` + `batchCreateUnsubscribeTokens` for the eligible winners. All three failure paths log a structured `[TRACKING_BREAK]` warning so any future regression is grep-able in prod logs (previously the bug was invisible: no error, no metric — just silent zeroes in `campaign_stats`). Defensive guard logs `[TRACKING_BREAK]` if `trackClicks=true` but `linkMap.size===0 && !mta.trackingDomain` at send time — that combination must never reach `sendEmailWithNullsink`. **Important contract**: `subscriberId` is set inside `sendEmail`/`sendEmailWithNullsink` per-call (not in the shared `trackingOpts`), so the same `trackingOpts` object is safe to reuse across the bounded-parallel SMTP fan-out workers. **Historical data is unrecoverable** — emails already left with the wrong HTML; only post-fix sends will be tracked correctly.
