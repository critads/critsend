# Critsend - Email Marketing Platform

## Overview

Critsend is an email marketing platform designed for efficient management and engagement of large subscriber bases. It offers comprehensive subscriber management with tag-based segmentation, a user-friendly campaign creation wizard, and flexible Mail Transfer Agent (MTA) configurations. The platform supports high-volume email sending with configurable speeds, detailed tracking (opens/clicks), and automatic unsubscribe handling. Key features include production-grade CSV import/export with batch processing, a complete REST API for integration, and capabilities to ensure email deliverability and data integrity. The business vision is to provide a scalable, reliable, and feature-rich solution for businesses to effectively communicate with their audience, driving engagement and marketing success.

## System Architecture

The Critsend platform uses a modern web stack: React, TypeScript, Vite, TailwindCSS, and Shadcn/UI for the frontend, and Express.js with TypeScript for the backend. PostgreSQL, managed with Drizzle ORM, serves as the primary data store, optimized for large datasets with advanced indexing. The system supports multi-user access with session-based authentication and AES-256-GCM encryption for sensitive data.

**UI/UX Decisions:**
The UI/UX follows Material Design 3 principles, featuring a clean, modern aesthetic with dark/light mode support, full mobile responsiveness, and a card-based layout. It uses Inter for text and JetBrains Mono for technical displays, with blue as the primary accent color.

**Technical Implementations & Design Choices:**
- **Authentication:** Session-based authentication with bcrypt for password hashing. All API routes require authentication, except public tracking, webhooks, health, and metrics endpoints.
- **Subscriber Management:** Features tag-based segmentation with GIN-indexed tags, a refs system for segment targeting, and a 7-day cooling-off period for unsubscribed contacts.
- **Campaign Management:** A 5-step wizard for campaign creation, including a WYSIWYG HTML editor and MTA selection. Supports A/B testing with variant tracking and automated winner declaration.
- **Email Sending:** High-performance sending via Nodemailer with configurable speeds and connection pooling. Supports concurrent campaign processing with a two-path architecture (in-memory nullsink and real SMTP).
- **Tracking:** Implements open tracking (1x1 pixel) and click tracking (redirects with open-redirect prevention). All tracking URLs are HMAC-SHA256 signed. **Single chokepoint invariant (Task #185):** every outbound email path — bulk campaign sender, pressure-guard drain worker, automation engine, Resend fallback, and (opt-in) test sends — funnels through `prepareTrackedHtml` in `server/email-service.ts`. That helper is the only place that runs `personalize → image rewrite → unsubscribe URL resolution → tracking pixel + click rewriting → footer`. Adding a new send path? Use this helper or your emails will silently lose tracking — there's a guard test in `tests/prepare-tracked-html.test.ts` that asserts the pixel is injected and raw `<a href>` URLs are rewritten. Test sends default to **no** tracking (untracked preview) but accept an explicit `trackInTest: true` opt-in; the opt-in requires a saved `campaignId` (and looks up the recipient by email, or accepts an explicit `subscriberId`) so the tracking events can satisfy the `campaign_stats` / `campaign_sends` FK constraints. Automation `send_email` steps lazy-create one synthetic `campaigns` row per workflow (status `automation_internal`, hidden from `getCampaignsPaginated`) cached on `automation_workflows.tracking_campaign_id` so opens/clicks generated by automation are persistable. Captures enriched context (IP, country, device, browser, OS) and uses a link registry for opaque UUID tokens in tracking links, along with branded short tracking URLs. Tracking events are buffered in-memory and flushed in batched multi-row inserts to a dedicated `pg.Pool` for isolation. Engagement counters are cached on the `campaigns` table and a 15-min counter-drift reconciler ensures data consistency. **FBL complaints are treated as plain unsubscribes on the subscriber side**: the campaign's standard unsubscribeTag is added (no `STOP-` prefix, no 7-day `suppressed_until` window) so existing segment exclusions naturally drop complainers. Campaign-level `complaints_count` and per-event `campaign_stats(type='complaint')` rows continue to be recorded so deliverability dashboards still distinguish complaints from unsubscribes. Pre-existing historical `STOP-*` tags on subscribers are preserved (no migration).
- **Segmentation (DSL v2):** Employs a recursive rule DSL for advanced segmentation with nested groups (AND/OR combinators, max 3 depth) and server-side pagination for segments. Includes targeted, cached subscriber counts with auto-invalidation.
- **CSV Import/Export:** Unified CSV format with auto-detection for refs and tags. Uses PostgreSQL COPY for high-performance imports with chunked file uploads, tag mode, pre-import operations, email deduplication, and live row counters. Supports forced tags/refs and removal of tags/refs.
- **Job Queues:** Dual-mode system with PostgreSQL-backed queues (SKIP LOCKED and LISTEN/NOTIFY) and optional BullMQ + Redis for advanced features. The campaign **sender** claim (`claimNextJob` in `server/repositories/job-repository.ts`) is FIFO by `campaigns.created_at`, but with an **aged-job fairness tie-breaker**: any job pending longer than `JOB_FAIRNESS_PROMOTE_MIN` minutes (default 15) is promoted ahead of the created_at FIFO. This prevents an old, perpetually-re-enqueuing campaign from starving requeued/younger campaigns (a freshly re-enqueued job is not aged, so it can't preempt a long-waiting one). This is independent from the pressure-guard **drain** FIFO. Never mutate `campaigns.created_at` to reprioritize — it is the immutable launch-ancestry key both the sender FIFO and the drain's deferred-subscriber serialization depend on.
- **Automation Workflows:** Trigger-based email sequences with a multi-step workflow builder.
- **Advanced Analytics:** Comprehensive analytics including engagement trends, cohort analysis, deliverability, and subscriber growth.
- **Prometheus Metrics:** Full observability via a `/metrics` endpoint and an in-app **System Metrics** dashboard displaying key performance indicators.
- **Security:** CSRF protection, Helmet.js security headers with CSP, CORS, extensive input validation, HTML sanitization, 5-tier rate limiting, secure session management, and webhook authentication.
- **Maintenance — `tracking_tokens` daily purge:** `tracking_tokens` is excluded from the 6h maintenance cycle and purged once a day at **01:00 Europe/Paris** by a dedicated scheduler in `server/workers.ts` (`scheduleDailyTrackingTokenPurge`). Rationale: the table grows ~5 GB/day and a multi-hour DELETE must never land in business hours. Retention is controlled by `TRACKING_TOKEN_RETENTION_DAYS` (default 90; prod set to 14) and per-run cap by `TRACKING_TOKEN_MAX_DELETE_PER_RUN` (default 5M; bump higher to catch up an existing backlog). Multi-process safety: all 3 PM2 processes arm a 01:00 timer, but only the first one to land actually runs — a `SELECT 1 FROM db_maintenance_logs WHERE table_name='tracking_tokens' AND status IN ('success','partial') AND executed_at > NOW() - INTERVAL '23 hours'` gate skips losers. DELETE LIMIT is already concurrency-safe, the gate just avoids wasted work. Each run writes a `db_maintenance_logs` row with `triggered_by='daily_1am_paris'` for observability.
- **Robustness:** Includes graceful shutdown, memory monitoring with load shedding, automated campaign auto-resume (MTA down + DB connection errors), bounce webhook idempotency, and bulk-optimized batch webhook processing. Web-process guardians rescue stuck import and campaign jobs. Startup bootstrap migrations use advisory locks and `CREATE INDEX CONCURRENTLY` for safety. Transient DB errors during campaign sending are re-thrown to the job-level handler which requeues with exponential backoff instead of permanently pausing campaigns.
- **Repository Pattern:** Storage layer decomposed into focused repository modules for subscriber, campaign, import, MTA, job, and system management.
- **Data Integrity & Concurrency:** Utilizes PostgreSQL's transactional capabilities, atomic counter updates, unique indexes, and optimistic locking.
- **Real-Time SSE Progress:** Server-Sent Events push instant progress updates for import, flush, and campaign jobs, with Redis integration for split-process mode.
- **Process Separation:** Supports a split-process architecture with dedicated web server and worker processes, utilizing Neon's PgBouncer pooled endpoints for database connections.
- **Pool Saturation Safety Net:** Layered defenses (connection timeouts, load shedding, request lease tracking, bounce webhook buffering) prevent pool starvation and ensure service availability, with detailed Prometheus metrics for monitoring.
- **Resilience & Observability (Tasks #148, #152-#154, #160-#161, #173):** A series of production-incident-driven hardening passes covering 503-attribution traceability, bootstrap-lock self-heal for PgBouncer transaction pooling, parallelized pressure-guard drain (drain-level + SMTP-level fan-out), drain process isolation in a dedicated PM2 process, real-time snowball ratio computation, drain tracking-parity restoration, and pressure-drain head-of-line blocking fix (volume-priority + fairness ordering + winding-down back-pressure). Full forensic detail (root causes, evidence, fixes, contracts) lives in **[`docs/architecture-history.md`](docs/architecture-history.md)** to keep this file light.
- **Nullsink SMTP Testing:** An internal SMTP server allows for testing campaigns without sending real emails.
- **Marketing Pressure Guard:** Hard 4h gap (was 6h until 2026-05-23; production constant in `server/services/pressure-guard.ts`, `PRESSURE_WINDOW_HOURS` env honoured only in non-prod) between any two emails to the same contact across **all** campaigns. Atomic CAS `pressureGuardReserveSendSlots` updates `subscribers.last_sent_at` only when eligible; losers enqueued as deferred sends (`campaign_sends.eligible_at = last_sent_at + window`). A drain worker picks campaigns by **volume priority** (drainable_count DESC) with a configurable **fairness slice** (`PRESSURE_GUARD_FAIRNESS_PCT`, default 20% of slots reserved for oldest-FIFO `campaigns.created_at` ASC). NOT `started_at` — sender rewrites `started_at` on relaunch, destroying FIFO. Campaigns with small persistent residual queues (`pending_count < 100` AND drainable < 50 continuously for >= 24h) enter **winding-down** state and are back-pressured to 1 tick out of every 4 so they cannot starve `MAX_CAMPAIGNS` slots from younger campaigns with large backlogs. Re-checks unsubscribe/suppression at dispatch, cascades infinitely. Drain runs in a dedicated PM2 process when `DRAIN_PROCESS_DEDICATED=true` (prod), else embedded in worker/web. **Architectural rule**: any singleton background job through Neon's PgBouncer pooled URL MUST use a lease-table-based leader election (`pressure_guard_leader`), NEVER session-level `pg_try_advisory_lock` (leaks indefinitely on transaction-pooled backends). The per-subscriber `pg_advisory_xact_lock` inside `pressureGuardReserveSendSlots` is safe — xact-scoped, auto-released at COMMIT. Counters (`campaigns.deferred_count`), Prometheus metrics, per-campaign `/api/campaigns/:id/queue`, admin `/api/admin/pressure-queue`, per-subscriber "next eligible", and an audit table (`pressure_flush_audit`) for manual flushes are exposed. See `docs/architecture-history.md` for the full forensic history (Tasks #149, #152-#154, #160-#161, #173).
- **Self-Hosted Deployment:** Provided `deploy/` directory includes PM2 configuration, Nginx setup, idempotent bootstrap script, deployment script, and GitHub Actions workflow for automated deployments.
- **PMTA Queue Monitoring (Task #193):** Background collector in `server/services/pmta-collector.ts` SSHes into the PMTA 4.5 host every 5 minutes (`PMTA_COLLECTOR_INTERVAL_MS`, default 300s) and runs `pmta show queue <domain>` for each domain in `PMTA_DOMAINS` (comma-separated, validated against `/^[a-z0-9.-]+$/i` to prevent shell injection). The parser extracts a pending count from PMTA summary lines (`Total messages`, `kmsg`, `N messages queued`, falling back to recipient-like row count) and greps for the regex `\b(error|timeout|refused|blocked|defer|421|450|451|452|550|554)\b` to surface error lines. One snapshot row per (domain, tick) is persisted to `pmta_queue_snapshots`. **Architectural rule (repeated here because it has bitten us twice — pressure-guard drain and now this):** singleton scheduling across the 3 PM2 processes uses a lease-table leader election (`pmta_collector_leader`), NEVER `pg_try_advisory_lock` (leaks on Neon's PgBouncer transaction pooling). **HTTP contract:** `GET /api/pmta/snapshots/latest` and `GET /api/pmta/snapshots/:domain/history` serve cached rows only — they NEVER open an SSH connection on the request path. `POST /api/pmta/refresh` (rate-limited 6/min) triggers an immediate forced tick. Required secrets: `PMTA_SSH_HOST`, `PMTA_SSH_PORT` (default 22), `PMTA_SSH_USER`, `PMTA_SSH_PRIVATE_KEY` (raw PEM, never logged), `PMTA_DOMAINS`. Frontend page at `/pmta` (TanStack Query, 30s polling) shows pending count, error count, status badge per domain, and a drawer with matched error lines + raw output excerpt. Parser regression coverage in `tests/pmta-parser.test.ts`.

## External Dependencies

- **PostgreSQL (Neon):** Primary database, hosted on Neon Launch plan, configured for SSL.
- **Nodemailer:** Used for real SMTP email sending with pooling and retries.
- **`sanitize-html`:** For sanitizing HTML content in campaigns.
- **`connect-pg-simple`:** For persistent session management using PostgreSQL.
- **`bcrypt`:** For secure password hashing.
- **`helmet`:** For HTTP security headers.
- **`prom-client`:** Prometheus metrics client for Node.js.
- **Object Storage for CSV imports:** Selected via `STORAGE_BACKEND` env var. Production runs on `hetzner` (Hetzner Object Storage, S3-compatible) to eliminate "CSV file not found" errors that occurred with local-disk storage when files disappeared between upload and worker pickup. Required env vars: `HETZNER_S3_{ENDPOINT,REGION,BUCKET,ACCESS_KEY,SECRET_KEY}`. Activation guide: `deploy/HETZNER_S3_SETUP.md`. Implementation in `server/storage-backends/hetzner-s3.ts` (multipart uploads, bounded timeouts, typed errors — `ObjectStorageAccessError` / `ObjectStorageTransientError` / NotFound — so the requeue route can distinguish "user must re-upload" from "operator must fix env/IAM" from "client should retry"). **Throttle hardening (2026-05-31):** Hetzner returns `503 SlowDown` under bursts of concurrent multipart PUTs, which crashed *every* import at once. Two-layer fix:
1. **Backend retry** (`server/storage-backends/hetzner-s3.ts`): S3Client `retryMode: "adaptive"` (client-side rate limiter for throttle storms) + `maxAttempts` raised 4→8, plus a `withTransientRetry` wrapper on every op that retries ONLY `ObjectStorageTransientError` with bounded exponential backoff+jitter (the upload op recreates the read stream each round; consumed streams can't replay). Tunables: `HETZNER_S3_{MAX_ATTEMPTS,RETRY_ROUNDS,RETRY_BASE_MS,RETRY_MAX_MS}`. Factory in `server/storage-backends/index.ts`.
2. **Deferred upload to worker (2026-05-31):** the original synchronous-request-path upload (`POST /api/import` + chunked-complete handler) had no requeue path, so a transient 503 past the backend retries permanently `failed` the job ("Import setup failed" → later "CSV file not found, re-upload") and a sustained storm risked pushing handler latency past the proxy timeout. Now both entry points only persist the file to the local staging volume and enqueue the queue row pointing at the **local** path (returning 202 immediately); the object-storage upload runs as the **first step of the worker job** via `ensureCsvUploadedToObjectStorage` in `server/services/import-processor.ts` (upload → verify with `objectExists` → atomically rewrite `import_job_queue.csv_file_path` to `/objects/...` → unlink local temp). It is idempotent (no-op for `phase2_merge`, already-`/objects/` paths, and the local-disk backend) so requeue/recovery re-entry is safe. On `ObjectStorageTransientError` the worker `.catch` requeues via `requeueImportJobForRetry(queueId, WORKER_ID)` instead of failing, bounded by a **wall-clock** window (`IMPORT_UPLOAD_MAX_RETRY_MS`, default 2h, from `created_at`). Correctness rules: the requeue is **lease-bound** (`AND worker_id = WORKER_ID`, returns boolean — if `recoverStuckImportJobs` already re-claimed a >10-min-stalled upload, it matches 0 rows and the caller must NOT fail the job); it deliberately does **NOT** touch `retry_count` (owned by `recoverStuckImportJobs`, which hard-fails a stuck `processing` row at `retry_count >= 2` — sharing it caused premature failure during storms); and a terminal failure deterministically unlinks the orphaned local staging file. Valid because `critsend-web`/`worker`/`drainer` are separate PM2 processes on one VM sharing a persistent `IMPORT_UPLOAD_DIR` volume. (`server/services/import-worker.ts` is dead code; the active processor is `import-processor.ts` driven by `server/workers.ts`.) Residual risk: no periodic sweeper for files orphaned by a crash mid-upload. Fallback options: `local` (writes to `IMPORT_UPLOAD_DIR`) and `replit` (Replit App Storage, Replit deployments only).
- **`geoip-lite`:** Local database for IP address to country/city lookup.
- **`ua-parser-js`:** For parsing user agent strings to extract device, browser, and OS information.
