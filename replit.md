# Critsend - Email Marketing Platform

## Overview

Critsend is an email marketing platform designed for efficient management and engagement of large subscriber bases. It offers comprehensive subscriber management with tag-based segmentation, a user-friendly campaign creation wizard, and flexible Mail Transfer Agent (MTA) configurations. The platform supports high-volume email sending with configurable speeds, detailed tracking (opens/clicks), and automatic unsubscribe handling. Key features include production-grade CSV import/export with batch processing, a complete REST API for integration, and capabilities to ensure email deliverability and data integrity. The business vision is to provide a scalable, reliable, and feature-rich solution for businesses to effectively communicate with their audience, driving engagement and marketing success.

## System Architecture

The Critsend platform uses a modern web stack: React, TypeScript, Vite, TailwindCSS, and Shadcn/UI for the frontend, and Express.js with TypeScript for the backend. PostgreSQL, managed with Drizzle ORM, serves as the primary data store, optimized for large datasets with advanced indexing. The system supports multi-user access with session-based authentication and AES-256-GCM encryption for sensitive data.

**UI/UX Decisions:**
The UI/UX follows Material Design 3 principles, featuring a clean, modern aesthetic with dark/light mode support, full mobile responsiveness, and a card-based layout. It uses Inter for text and JetBrains Mono for technical displays, with blue as the primary accent color.

**Technical Implementations & Design Choices:**
- **Authentication:** Session-based authentication with bcrypt for password hashing. All API routes require authentication, except public tracking, webhooks, health, and metrics endpoints.
- **Subscriber Management:** Features tag-based segmentation with GIN-indexed tags, a refs system for segment targeting, and a 7-day cooling-off period for unsubscribed contacts.
- **Campaign Management:** A 5-step wizard for campaign creation, including a WYSIWYG HTML editor and MTA selection. Supports A/B testing with variant tracking and automated winner declaration.
- **Email Sending:** High-performance sending via Nodemailer with configurable speeds and connection pooling. Supports concurrent campaign processing with a two-path architecture (in-memory nullsink and real SMTP).
- **Tracking:** Implements open tracking (1x1 pixel) and click tracking (redirects with open-redirect prevention). All tracking URLs are HMAC-SHA256 signed. Captures enriched context (IP, country, device, browser, OS) and uses a link registry for opaque UUID tokens in tracking links, along with branded short tracking URLs. Tracking events are buffered in-memory and flushed in batched multi-row inserts to a dedicated `pg.Pool` for isolation. Engagement counters are cached on the `campaigns` table and a 15-min counter-drift reconciler ensures data consistency. **FBL complaints are treated as plain unsubscribes on the subscriber side**: the campaign's standard unsubscribeTag is added (no `STOP-` prefix, no 7-day `suppressed_until` window) so existing segment exclusions naturally drop complainers. Campaign-level `complaints_count` and per-event `campaign_stats(type='complaint')` rows continue to be recorded so deliverability dashboards still distinguish complaints from unsubscribes. Pre-existing historical `STOP-*` tags on subscribers are preserved (no migration).
- **Segmentation (DSL v2):** Employs a recursive rule DSL for advanced segmentation with nested groups (AND/OR combinators, max 3 depth) and server-side pagination for segments. Includes targeted, cached subscriber counts with auto-invalidation.
- **CSV Import/Export:** Unified CSV format with auto-detection for refs and tags. Uses PostgreSQL COPY for high-performance imports with chunked file uploads, tag mode, pre-import operations, email deduplication, and live row counters. Supports forced tags/refs and removal of tags/refs.
- **Job Queues:** Dual-mode system with PostgreSQL-backed queues (SKIP LOCKED and LISTEN/NOTIFY) and optional BullMQ + Redis for advanced features.
- **Automation Workflows:** Trigger-based email sequences with a multi-step workflow builder.
- **Advanced Analytics:** Comprehensive analytics including engagement trends, cohort analysis, deliverability, and subscriber growth.
- **Prometheus Metrics:** Full observability via a `/metrics` endpoint and an in-app **System Metrics** dashboard displaying key performance indicators.
- **Security:** CSRF protection, Helmet.js security headers with CSP, CORS, extensive input validation, HTML sanitization, 5-tier rate limiting, secure session management, and webhook authentication.
- **Robustness:** Includes graceful shutdown, memory monitoring with load shedding, automated campaign auto-resume (MTA down + DB connection errors), bounce webhook idempotency, and bulk-optimized batch webhook processing. Web-process guardians rescue stuck import and campaign jobs. Startup bootstrap migrations use advisory locks and `CREATE INDEX CONCURRENTLY` for safety. Transient DB errors during campaign sending are re-thrown to the job-level handler which requeues with exponential backoff instead of permanently pausing campaigns.
- **Repository Pattern:** Storage layer decomposed into focused repository modules for subscriber, campaign, import, MTA, job, and system management.
- **Data Integrity & Concurrency:** Utilizes PostgreSQL's transactional capabilities, atomic counter updates, unique indexes, and optimistic locking.
- **Real-Time SSE Progress:** Server-Sent Events push instant progress updates for import, flush, and campaign jobs, with Redis integration for split-process mode.
- **Process Separation:** Supports a split-process architecture with dedicated web server and worker processes, utilizing Neon's PgBouncer pooled endpoints for database connections.
- **Pool Saturation Safety Net:** Layered defenses (connection timeouts, load shedding, request lease tracking, bounce webhook buffering) prevent pool starvation and ensure service availability, with detailed Prometheus metrics for monitoring.
- **503 Attribution (Task #148):** Every `503 service_busy` response funnels through `server/middleware/service-busy.ts` (`emitServiceBusy` / `recordServiceBusy`). One structured `[503]` log line per emission (with rid/method/path/route/source/kind/code/pool active+idle+total+waiting+saturation/lease — guaranteed per-request attribution from logs alone) + a 50-event in-memory ring buffer + the cross-cutting `critsend_service_busy_503_total{source,route}` counter make every emission attributable. Sources: `load_shed`, `lease_exceeded`, `checkout_timeout` (incl. `kind=upgraded_from_500` from the `poolErrorResponseUpgrade` patch), `handler_transient` (route-level transient DB error), `memory_pressure` (POST `/campaigns/:id/send`). Triage endpoint: **GET `/api/admin/503-attribution`** (admin-gated via `users.is_admin`/`ADMIN_USER_IDS`) returns total + per-source + per-route + per-pair counts plus the most-recent ring entries with rid, route, pool snapshot and lease holding. Frontend `apiRequest` now throws `ApiError` (with `.status` + parsed `.body`); the `/campaigns` page recognises 503 service_busy and shows a soft "Serveur momentanément occupé — Nouvelle tentative…" panel instead of the red error banner. The counter-reconciler push-downs the `recent_campaigns` filter INTO each `truth` CTE so each tick scans the active subset (~100 campaigns) instead of the full 20 M-row `campaign_stats` table — eliminating the recurring `statement_timeout` ticks that previously consumed a pool slot for 120 s. POST `/api/campaigns` validates `segmentId` + `excludeSegmentId` in a single `WHERE id = ANY(...)` round-trip so the route stays under the 2-checkout-per-request lease cap.
- **Nullsink SMTP Testing:** An internal SMTP server allows for testing campaigns without sending real emails.
- **Pressure-Guard SMTP Fan-Out (Task #154):** During the same 2026-05-14 prod incident the parallelized drain (Task #153) was confirmed running with `drained_calls=9` per tick, but cumulative throughput plateaued at ~800-3500 sends/min — far below the 24k/min projection. Root-cause: inside `drainCampaign`, the SMTP dispatch loop was **strictly sequential** (`for (const sub of eligibleSubs) { await sendEmailWithNullsink(...) }`), so each send waited for the previous SMTP RTT (~100ms) before starting the next. Per-campaign ceiling = ~10 sends/sec, × DRAIN_PARALLELISM=4 = ~2,400/min — exactly the observed rate. **Fix**: bounded-parallel SMTP fan-out inside `drainCampaign` using the same worker-pool pattern as Task #153 but at the per-send level. N workers (default `PRESSURE_GUARD_SMTP_CONCURRENCY=20`, hard-capped at 100) pull from a shared `sendQueue` of eligible subscribers; SMTP I/O is interleaved while Node's single-threaded event loop keeps `successIds`/`failedIds`.push race-free between awaits. With DRAIN_PARALLELISM=4 × SMTP_CONCURRENCY=20 the theoretical cluster-wide ceiling becomes ~80 simultaneous SMTP sends → ~24k sends/min. Peak fan-out is bounded by the Nodemailer pool per MTA (typically 5-10 conn × 7 MTAs = 35-70 sockets) so the 80 cap fits comfortably. The env var is persisted in both `critsend-web` and `critsend-worker` env_production blocks of `deploy/ecosystem.config.cjs`. Startup log line now includes `smtp-concurrency=N`. Diagnostic note: the previous bottleneck was invisible in the standard tick log (`drained_calls=N` counts `drainCampaign` invocations, not actual SMTP sends), so the symptom was "drain looks healthy but backlog grows" — only the per-MTA `recent_sent` query revealed the throughput plateau. Companion lesson: if the deferred queue starts to grow despite `leader_acquired=Y` and non-zero `drained_calls`, check the actual sends/min via `SELECT date_trunc('minute', sent_at), COUNT(*) FROM campaign_sends WHERE sent_at > NOW() - INTERVAL '10 min' AND status='sent' GROUP BY 1` before assuming the drain is broken.
- **Pressure-Guard Drain Parallelization (Task #153):** The pressure-guard deferred-drain worker (server/workers/pressure-guard-worker.ts) previously processed eligible campaigns strictly sequentially — `for (const row of campaignsRes.rows) { await drainCampaign(...) }` — which capped per-tick throughput at ~1 campaign × BATCH rows / drain-duration. Constated during the 2026-05-14 prod incident: 10+ massive campaigns launched in parallel at 12:32-12:34 UTC on overlapping audiences pushed 810k rows into the deferred queue (321k immediately `due_now`, 488k still inside the 6h pressure window), but the sequential drain produced only ~1500 sends/min total — projected ~3-4 hours to drain. **Fix**: bounded-parallel drain with a fixed concurrency cap. The drain loop now spawns N workers (default `PRESSURE_GUARD_DRAIN_PARALLELISM=1`, prod set to 4 via deploy/ecosystem.config.cjs) that pull from a shared queue of eligible campaign IDs. Each `drainCampaign(campaignId)` call peaks at ~2 main-pool connections (claim txn + finalize txn; SMTP send is external I/O), so DRAIN_PARALLELISM=4 holds peak DB footprint at ~8 connections — well within the 30-slot main pool. JS single-threaded execution makes the `drainedCalls`/`errorCount` shared counter increments race-free despite interleaved awaits. The cap is hard-clamped to 16 to prevent runaway pool saturation if misconfigured. Companion change: deploy/ecosystem.config.cjs now persists the production-tuned drain knobs (`PRESSURE_GUARD_POLL_MS=10000`, `PRESSURE_GUARD_BATCH=1000`, `PRESSURE_GUARD_MAX_CAMPAIGNS=20`, `PRESSURE_GUARD_DRAIN_PARALLELISM=4`) into both `critsend-web` and `critsend-worker` env_production blocks so they survive `pm2 reload` / restart cycles (previously the same values were applied via one-shot `pm2 restart all --update-env` which is lost on the next ecosystem reload). All four are dotenvVars-overridable, so `.env` still wins for ad-hoc tuning. The "Starting" log line now includes `drain-parallelism=N` so per-process configuration is grepable. **Architectural note**: the drain is started from BOTH the web (DISABLE_WORKERS branch in server/index.ts) AND the worker process; only one acquires the leader lease at a time (Task #149 lease table), so the env vars MUST match on both sides — they do, via the shared dotenvVars+default mechanism.
- **Bootstrap Lock Self-Heal (Task #152):** At every web/worker process boot, `releaseStuckBootstrapLocks()` (server/bootstrap-lock-recovery.ts) preemptively `pg_terminate_backend`s any idle PgBouncer-labelled backend (`application_name='pgbouncer'`, `state IN ('idle','idle in transaction','idle in transaction (aborted)')`) still holding a session-level advisory lock in our reserved bootstrap range (objids 900001-900020). This neutralises the Neon-PgBouncer transaction-pooling leak that `withAdvisoryLock` (server/bootstrap-lock.ts) suffers from on every `pm2 reload`: the previous process's `pg_try_advisory_lock(<objid>)` lands on backend X via PgBouncer, the Node process exits, but PgBouncer keeps backend X alive (idle) and the session lock leaks indefinitely — the next process boots, tries `pg_try_advisory_lock` on a different backend, gets `acquired=false`, logs "Another process is running bootstrap — skipping" and bails, so the bootstrap DDL never runs on the new code. Without this self-heal, Task #149's deploy hung in production with `pressure_guard_leader` table never created and `bootstrap=pending → deferred` looping every 15s for 6+ minutes until manual `pg_terminate_backend` via psql freed the leaked PIDs (constated 16564/16571/16609 holding objids 900004/900005/900015). The self-heal SQL is identical to `POST /api/admin/pressure-guard/release-stuck-locks` (still kept as a manual one-shot escape hatch, but no longer needed during normal deploys) but generalised to the full 900001-900020 range and called automatically. Best-effort: never throws, 5s `statement_timeout`, terminates only `application_name='pgbouncer'` idle backends so direct app connections are never touched. Logs `[LOCK_RECOVERY] (web-boot|worker-boot) terminated N leaked PgBouncer backends … by_objid={…}` on every boot for observability.
- **Marketing Pressure Guard:** Hard 6h gap (configurable via `PRESSURE_WINDOW_HOURS`) between any two emails to the same contact across **all** campaigns. The atomic CAS `pressureGuardReserveSendSlots` updates `subscribers.last_sent_at` only when the contact is currently eligible; losers are enqueued as deferred sends (`campaign_sends.eligible_at = last_sent_at + window`). A 30s drain worker picks deferred sends up FIFO by `campaigns.started_at`, re-checks unsubscribe/suppression at dispatch, and cascades infinitely. **The drain worker is started from BOTH the dedicated worker process (`startAllWorkers`) AND the web/`DISABLE_WORKERS=true` branch in `server/index.ts`** so deferred rows are still consumed in split-process or web-only deployments. **Leader election (Task #149)** uses a `pressure_guard_leader (lock_key text PK, holder_id text, expires_at timestamptz)` lease table with atomic `INSERT … ON CONFLICT DO UPDATE WHERE expires_at < NOW() OR holder_id = $1`; the lease is refreshed in a background timer at TTL/3 (default TTL=60s) and best-effort released on completion, with auto-recovery via TTL after a node crash. The previous `pg_try_advisory_lock(LOCK_KEYS.PRESSURE_DRAIN)` session-level approach was incompatible with Neon's PgBouncer transaction-pooled endpoint — every `client.query` is routed to a different physical backend, so acquired locks leaked indefinitely on the original backend (constated PIDs 15115/16609 stuck in prod, idle, executing unrelated `application_name=pgbouncer` queries) and the worker silently bailed on every tick, freezing the drain at ~92k due-now rows. **Architectural rule**: any future "leader election" / "singleton background job" running through the Neon pooled URL MUST be lease-table-based, never session-advisory-lock-based. The same `withLeaderLease` helper now backs the `PRESSURE_DRAIN`, `PRESSURE_MAINTENANCE` and `PRESSURE_AUDIT_TTL` cadenced jobs. The drain worker emits a single-line `[PRESSURE_GUARD_WORKER] tick: leader_acquired=Y/N, bootstrap=…, has_pending=Y/N, eligible_campaigns=N, drained_calls=N, errors=N` summary on every tick (drain or no drain) so a future silent-bail is immediately distinguishable from a healthy idle worker via `pm2 logs … | grep PRESSURE_GUARD_WORKER`. A one-shot admin route `POST /api/admin/pressure-guard/release-stuck-locks` (admin-gated via `users.is_admin`/`ADMIN_USER_IDS`) terminates idle PgBouncer backends still holding the legacy advisory locks (objids 900014/900015/900016) post-deployment. Counters (`campaigns.deferred_count`) plus Prometheus metrics, a per-campaign `/api/campaigns/:id/queue` view, an admin `/api/admin/pressure-queue` cross-campaign view, and a per-subscriber "next eligible" endpoint are exposed; an audit table records every manual flush. The per-subscriber `pg_advisory_xact_lock` used inside `pressureGuardReserveSendSlots` is intentionally untouched — it is xact-scoped, so PgBouncer auto-releases it at COMMIT/ROLLBACK and is safe with transaction pooling.
